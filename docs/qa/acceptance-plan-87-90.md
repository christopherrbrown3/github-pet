# Functional acceptance plan: #87 Settings panes, #87 Inbox redesign, #90 Sparkle auto-update

Written 2026-11-20 from the issue acceptance criteria on main 96b70d0. Plan only: nothing here has been run. It extends `acceptance-matrix.md` (which still defines PASS/FAIL/BLOCKED and the run record) and applies to the exact PR head SHAs the PM routes. Branch names: `feat/87-settings-panes`, `feat/87-inbox-redesign`, `feat/90-update-check`.

## Evidence rules (as in PR75/PR86 reports)

Each report states: exact head SHA and base, exact CI run ID and conclusion for that SHA, macOS/Swift versions, build commands with exit codes, SHA-256 of any built `.app` zip or binary used, the defaults suite, and per case PASS / FAIL / BLOCKED with the method used. Always say which tier produced the evidence (below) and what was **not** verified. A snapshot PNG is not evidence of interaction, motion or keyboard/VoiceOver behavior. Never delete or reset preference plists; list any left behind for Chris. No network, no real account, synthetic data only.

| N | `--render-snapshots <dir>` / `scripts/render-check.sh`: fixture scenario, light and dark PNGs, AX tree dump, report text | Dark/light stills, AX labels and values of the real views, privacy redaction in AX text | Interaction, motion, focus order, actual VoiceOver speech |

## #90 Sparkle 2 auto-update (scope changed 2026-11-20: supersedes the phase-1 check-only plan)

Chris's decision (#90 comment, 2026-11-20): Sparkle 2 automatic updates on the current **ad-hoc** builds. The first install is still approved once via System Settings → Privacy & Security → Open Anyway. The update trust root is Sparkle's **EdDSA signature**, not notarization; Sparkle clears quarantine on updates it installs (accepted, Sparkle-verified updates only). Feed is a static `appcast.xml` over HTTPS; archives are GitHub Release assets; prereleases use `<sparkle:channel>beta</sparkle:channel>`; install is user-confirmed by default (`SUAutomaticallyUpdate` = NO); system profiling off. #89 is post-beta. The replaced phase-1 wording ("a failed check never reads up to date", no auto-install) still applies in part, per UPD-03 and UPD-13; "no auto-install claims" is now "claims match what is implemented".

### Key handling and safety rules for QA (hard rules)

- QA uses only a **throwaway test EdDSA key** generated for the run (`generate_keys --account <unique test account>` in a scratch keychain, or a temp key file the developer's script supports), never the production key and never Chris's login-keychain production entry. If a run would need the production private key, stop and report BLOCKED. Never read, export, print or commit any private key. Record only the test public key.
- Test builds must be built with that test public key as `SUPublicEDKey` and a **file-served or localhost HTTPS-less feed only if the build allows it for tests**; do not modify committed Info.plist keys. If the build cannot be pointed at a test feed without code changes, that is a BLOCKED finding for the developer (a test-only override, e.g. an environment variable or launch argument, ignored in release builds).
- Isolated preferences: use `--defaults-suite <unique>`; real preferences (`dev.github-pet.GitHubPet`) are never touched. Sparkle keeps its own state in the app's defaults domain, so the updated-app tests must run with a copy of the test bundle ID or an isolated container as the developer documents; if the bundle ID cannot be isolated, record exactly which real domain the run would touch and stop for Chris. Never delete preference plists; list any left behind.
- Test appcast and archives live in a scratch directory outside the repository and are served from `file://` or a localhost server bound to 127.0.0.1 only. No production feed URL, no real GitHub Release assets and no network are needed for any test.

### Test rig (build-to-build)

1. Build app **N** (current SHA) and app **N+1** (a trivially different build: higher `CFBundleVersion`, e.g. changed `VERSION`) with `scripts/build-app.sh`, both ad-hoc signed and both embedding the test public key.
2. Zip N+1, sign with the test private key (`sign_update`), and write a test `appcast.xml` with the length and `sparkle:edSignature`; also create variants: tampered archive (flip a byte after signing), wrong-key signature, missing signature, same-version, older version, beta-channel item, and a malformed feed.
3. Install N in a scratch location (see UPD-S06 for the non-admin / non-`/Applications` variants), launch with an isolated suite, seed state, point the feed at the test appcast, run the update.
4. Record SHA-256 of every zip, the appcast and each built app's `codesign -dv` identity line, plus the exact test public key.

## Run order and handoff

1. Confirm the head SHA and CI conclusion for that exact SHA; merge-from-main status.
2. `swift build`, `scripts/test.sh`, `scripts/build-app.sh`, `scripts/render-check.sh`; record exit codes and artifact SHA-256.
3. Source review pass (tier S: INV-04/05/06, UPD-14/15/16/17 greps and packaging, settings parity INV-08).
4. Runner scenarios and snapshots (tier R/N), then the launched-app pass (tier A) for layout, keyboard, persistence, quiet/snooze with `--start-time`, and the update fault cases.
5. Report: verdict, per-ID results, defects with reproduction to t6f, and an explicit "not verified" list (real VoiceOver, real install/update, notarization, multi-display).
