# QA review: PR64 415496b (#7 access, SAML and rate-limit messages) and PR63 608adbe (#12 persistence)

QA: Claude Opus 5.5 (`claude-opus-5-5`), task M from PM t61, 2026-11-16. Both are source-only reviews; the reasons a functional run isn't possible are given below.

## PR64 415496b: PASS with one MED

- **CI:** 43896740914 completed SUCCESS on the exact head. It is a single commit on main 134cd57.
- **Precedence on the main query's stderr:**
  1. `authFailure` (401, bad credentials, exit-4 sign-in) → signedOut
  2. "rate limit" → rateLimited
  3. `deniesAccess` → accessDenied
  4. otherwise parse

  A rate-limit 403 therefore stays a rate limit. In the GraphQL `errors` member the order is RATE_LIMITED, then FORBIDDEN or INSUFFICIENT_SCOPES or denial wording, then graphQLError. The auth-status preflight checks rate limit, then denial, then network.
- **Fixed messages:** `accessDeniedMessage`, `rateLimitedMessage` and `accessDeniedQuality` are constants. gh's stderr and GitHub's messages are only *classified*, never displayed. A test asserts that `secret-org` doesn't leak.
- **Unknown stays failed:** with no viewer, no successful source and no specific issue, the result is still "Monitoring scope could not be verified" (a failure), never empty.
- **Evidence:** the before-behaviour probe shows SAML and rate-limit stderr falling through to "could not be verified". After the fix, 44 tests in 7 suites pass, and the CI-style full run passes 464.
- **MED-1: an access-denial stderr now discards partial data.** On a nonzero exit, `ScopedGhClient.run` returns `.failure(.accessDenied)` on the stderr text alone, **before** the stdout JSON is parsed (`ScopedGitHub.swift:316`).
  - When only one org in a Selected scope enforces SAML, `gh api graphql` exits 1. It prints "Resource protected by organization SAML enforcement…" to stderr *and* the response with data for the other targets to stdout.
  - Before this PR that parsed to Partial with fresh rows (`graphQLError`). Now the whole poll fails: `.failed(accessDenied)`, no fresh rows, and the "denied" message for the whole scope.
  - It still fails closed; nothing looks empty. But it loses usable data and is more severe than the actual problem.
  - Suggested fix: parse first. If a viewer and at least one successful source come back, add `.accessDenied` to the issues, which gives Partial with rows and the `accessDeniedQuality` line. Use the failure message only when nothing parses.
  - Add a test with a nonzero exit, SAML stderr, and stdout that has partial data.
  - The rate-limit early return has the same shape, but that behaviour predates this PR.
- **LOW-2: the "saml" substring is broad.** `deniesAccess` matches "saml" anywhere in stderr, and gh's per-target messages include names, for example "Could not resolve to an Organization with the login of 'saml-team'". Together with MED-1, a missing target whose name contains "saml" or "single sign-on" turns the whole poll into "access denied" instead of a target-unavailable result. Prefer the "saml enforcement" or "saml sso" phrases, or classify only from the `errors[].type`.
- **Functional: not possible safely.** The real `ScopedGhClient`, and with it `GITHUB_PET_GH_PATH`, is used only in a normal launch. `--simulate-monitoring-scope` uses the offline simulation, `--qa-scenario` is refused without it, and `--render-snapshots` forces fixtures and never launches gh. A fake-gh check would need a normal launch, which is prohibited. The Developer's runner-injected tests cover the classifications.

## PR63 608adbe: PASS

- **CI:** 43896478419 completed SUCCESS on the exact head. Two commits on main 5cf5185.
- **What is stored:**
  - **Digests only:** each item ID becomes a 128-bit SHA-256 prefix (`EventBaseline.digest`). The session key is a digest of the source, the account node ID (`storageSuffix`) and the sorted scope JSON. There are no titles, repositories, URLs or tokens (`recordContainsOnlyDigestsNoItemData`).
  - **Bounded:** at most 1024 digests and 64 KB per record, checked both on `load` and on `save`.
  - **Single slot:** `GitHubPet.event-baseline.v1`.
  - **Rejected records:** a record with another key, version, structure or size, or one that fails to decode, is `reset()` and nil is returned. The next snapshot then re-baselines silently.
- **Restore rules:**
  - **24 h window:** `restore` is accepted only while the session is Loading with no data and no tracker. The restored record is comparable only if its quality was complete (ready, empty or hiddenOnly), the baseline was established, and `0 ≤ now − lastSuccess ≤ 24 h`. Otherwise it re-baselines silently.
  - **Never looks empty:** a restored record keeps the state Loading; it is never shown as empty.
  - **Failures:** a failure clears `restoredQuality` and makes the result non-comparable.
- **Lifecycle:**
  - **Session changes:** a change of source, account or scope resets the repositories, then loads for the new key (deleting the other session's record).
  - **Clearing:** `--reset-settings` and Reset baseline clear the record.
  - **Writes:** identical saves are skipped.
- **Real domain untouched:** `LaunchOptions` forces snapshot launches onto the in-memory `EphemeralDefaults` render-snapshots suite with reset. Simulated launches use the in-memory scope-simulation suite and `cleanupScopeSimulation` removes it. CI's GUI render check ("saved preferences untouched") passed.
- **Tests and evidence:** 10 app-level and 13 core tests cover:
  - relaunch with nothing new, and an item announced exactly once
  - records older than a day, partial or stale quality, corrupt, oversized and other-version records
  - scope and account changes with no leakage, reset, and the snapshot launch staying in its throwaway domain

  Fail-before (`fail-before-core-only-no-appmodel.log`): the AppModel wiring was missing, so `load` returns nil. Targeted tests pass after (62 tests in 11 suites). The full suite fails only on the known in-process `/dev/fd` descriptor flake, which also fails on main 5cf5185 and which CI runs in isolation.
- **INFO:** the digests are unsalted. Anyone holding both the plist and candidate node IDs could confirm which items were seen. This is local-only and low risk.
- **INFO:** the single slot means switching A→B→A discards A's record, so A re-baselines silently. This is by design.
- **Functional: not possible safely.** Persistence across launches needs a domain that survives the process, but snapshot and simulated launches are deliberately in-memory and reset, and the QA runner requires simulation. A two-launch test would need normal launches with a private `--defaults-suite`, which our rules prohibit. The Developer's AppModel-level relaunch tests cover it.
