## PR50, local-only commit a1881806ce59a5fc15be8c1cd5bca0b47ad90876 (on 45befb4, not pushed)

The change is in `Sources/GitHubPetCore/MascotPack.swift:118,128-135`. The eight file-path error descriptions now use `PackLabel.sanitizePath` instead of `sanitize`:

- `sanitize` cuts after the first 48 graphemes, keeping the head.
- `sanitizePath` caps at 160 graphemes, keeping a 24-grapheme head, "…", and the tail.

| Check | Result |
|---|---|
| Distinct identities | Two long paths with a shared prefix now keep their different filename tails. This fixes the ambiguity QA reproduced in `docs/qa/pr50-45befb4/asset-error-ci`. The stored error value (`.missingFile(path)`) is unchanged, so matching and equality are unaffected. |
| Sensitive-path leakage | None. Every path in these errors comes from the manifest, is pack-relative and is written by the pack author (`MascotPack.swift:364-387`). `isSafeRelativePath` rejects absolute paths, `~`, `..` and control characters. The pack directory's host path is not part of these errors; it appears only in the existing launch line (`AppModel.swift:88`). |
| Label sanitizer policy | Unchanged. `q()`/`sanitize` still applies to state names, id and name. Paths get the same `clean()` treatment (controls become a space; format, bidi and private-use characters are dropped). The new test checks for no control or format characters. |

Findings:

- **LOW-1: very long paths can collide.** The tail is taken after the 2048-scalar cap is applied (`MascotPack.swift:59-66`). For a path longer than 2048 scalars, the "tail" is really the middle of the input. Two such paths that share their first 2048 scalars produce identical descriptions. Paths that differ only inside the elided middle (more than about 135 characters from the end) also collide. Both are bounded and cosmetic, and only an author-controlled malformed pack can trigger them.
- **LOW-2: rejection text is about 3× longer.** Each path entry can now be about 190 characters instead of about 70. The text is joined without a length limit into the Settings caption (`SettingsView.swift:28-31`) and the status line (`AppModel.swift:90`). A pack with many bad frames (up to 12 frames plus a fallback per state) produces a long caption. Consider limiting how many errors are shown, e.g. "+N more".

Verdict: no blocker. The fix does what it is meant to do and leaves sanitizer policy unchanged.

## PR59 d813f103b6c9f978a5a2c19e2591154972af95ba (base feat/30-scope-settings)

Measured against issue #35 decision 6903109382.

| Decision rule | Source | Result |
|---|---|---|
| Full cap is Partial | `ScopedGitHub.swift:186` treats `more` as capped, and so is `nodes ≥ 30` with `count > nodes`. Capped adds an issue, which makes the result Partial. | OK |
| Hidden requires a clean response | `ScopedGitHub.swift:189-191,217-231`: the hidden count is used only when `issues.isEmpty`. Otherwise every hidden alias is turned into capped (Partial). `outcome` passes hidden only when the response is complete (`:89`). `InboxEngine.swift:65-66` stores hidden only when complete. | OK |

The hover summary falls back to the status text. | OK, except MED-1 below |
| Any uncertainty is Partial | Scoped responses use strict number and boolean parsing (`ScopedGitHub.swift:106-115`, issueCount ≤ Int32.max). `count < nodes` is treated as malformed, and a malformed row makes it Partial. | OK |

| Privacy | Counts only (`Models.swift HiddenResults`). | OK |

Findings:

- **MED-1: overlap removal can produce All clear when counts disagree** (`ScopedGitHub.swift:219-226`).
  - A repo target whose verified owner is also a verified org target has its hidden count dropped entirely. This applies to both categories. The org search is assumed to cover it.
  - If GitHub's org count is lower than the repo count, the result is wrong. For example, org reviews report hidden 0 while a covered repo's reviews report hidden 3. With zero visible rows the state becomes `.empty`, which shows "All clear".
  - That contradicts "hidden-only never all-clear" and "when in doubt, Partial".
  - Suggested fix, per category: if a covered repo alias's hidden count is greater than its org alias's hidden count, either treat the alias as capped (Partial) or use the larger count. Add a regression test for the contradiction.
- **LOW-2: legacy client never checks `hasNextPage`.** The legacy query does not request `pageInfo` (`GitHubCLI.swift:133-138`), so a short page with more matches is classified as hidden, not capped. The decision's hidden case requires no `hasNextPage`. This is low because the app now constructs only `ScopedGhClient` (`AppModel.swift:119`), but the decision says the rule also applies to the legacy client.
- **LOW-3: legacy hidden sum can overflow.** `GitHubCLI.swift:192` decodes `issueCount` with Codable as an unbounded `Int`, and `hidden += total - nodeCount` across two pages can trap if gh returns values near Int.max. The scoped parser already bounds the count at Int32.max. The legacy path should use the same bound or saturating addition.
- **Note:** PR59 still needs the final PR51 commits merged in (7f12ebc and e57d1f3 are not in it), as the PM handoff already says.

Verdict: one medium decision-conformance finding (MED-1). Everything else matches the decision.
